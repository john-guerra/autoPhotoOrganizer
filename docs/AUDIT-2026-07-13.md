# Audit — 2026-07-13 (against v2.12.6)

Three independent reviews: a codebase/architecture audit, a feed-performance
diagnosis, and a triage of all 34 open GitHub issues. Everything below is
evidence-backed — file:line, a measurement, or a reproduction. Where a claim is
inferred rather than verified, it says so.

Ranked by **impact on the product goal × cost to fix**. The goal, from the
founding spec: fast, local-first triage of a 100k+ photo library, keyboard-first,
because Lightroom is too slow.

## P0 — correctness and data loss

### 1. A failed rating silently keeps the star lit

`ui/src/App.svelte` — `rate()` updates the local rating optimistically and never
reverts it if the write fails. The star stays lit, you keep culling, and the
export later ships the wrong set. In a rating-driven workflow that is silent data
loss with a fig leaf on it. **Fix:** revert the local value in `.catch` and
surface the failure. Minutes of work.

### 2. "Collapse all" is broken on a real library — reproduced

`applyViewModeToGroups` collapses every top-level group: with folder grouping on
the real index that is **1,183 paths**.

- The collapsed set rides a **GET query param** (`ui/src/lib/api.js`) — ~190KB
  URL-encoded against Node's 16KB header cap, so the request dies before Express.
- Even delivered, `exclusionClause` (`server/db/feed.js`) builds 1,183 AND'd
  `NOT(...)` terms and SQLite throws **"Expression tree is too large"**
  (reproduced with the real folder list).
- Below those cliffs, one `COUNT` query per collapsed path per page.

**Fix:** store the collapsed set server-side — `keep_scope` in `schema.js` is the
exact precedent — or add a `collapseAll` flag with group-level paging.

## P1 — the thesis isn't implemented

### 3. The RAW embedded-preview pipeline was never built

`CLAUDE.md` and the design doc claim exiftool-vendored in daemon mode.
**`exiftool-vendored` is not a dependency.** `extractPreview` uses
`exifr.thumbnail()` — the ~160px EXIF IFD1 thumbnail — which _throws_ for RAW.
So a RAW's only image anywhere in the app is a 160px thumb. Worse, the loupe
points its `<img>` at `/api/image/:id` (the original 25–50MB RAW the browser
cannot decode, with no `on:error`) and the ±3 prefetch does not skip RAW. "Never
fully decode a RAW" is currently "download every RAW, repeatedly, for nothing."
`/api/preview/:id` also has no disk cache, so it re-parses per request and is
absent from the offline mirror the second invariant promises.

**Fix:** add exiftool-vendored; extract `PreviewImage`/`JpgFromRaw` into the
thumbs cache; route the Thumb and Loupe RAW branches through it. Fix the docs in
the same commit. ~1 day, and it is the product's differentiator.

### 4. The scan doesn't render progressively

The recursive scan is the default and the SD-card path, and it `await`s the whole
job before the first `loadInitialFeed()` — the grid stays empty until the entire
walk finishes, violating "grid appears while scanning continues". The server
already streams per-folder progress over SSE; the client just ignores it.
**Fix:** refresh the feed on scan-progress ticks. Small.

### 5. Prefetch runway is shorter than one round trip

`FETCH_THRESHOLD = 20` display entries ≈ 400px of real runway after overscan. At
fling speed (3,000–6,000 px/s) that is <150ms — less than the fetch+render round
trip, so you outrun the feed even now that queries are fast. It is also
_entry_-count-based, so burst stacks shrink the runway further.
**Fix:** trigger on remaining laid-out pixels (~2 viewport-heights, using the
`boxes` y-coords already computed), optionally scaled by scroll velocity.

## P2 — process and safety nets

### 6. CI has no gates

`.github/workflows/ci.yml` runs prettier + vitest only. **No `vite build`, no
`svelte-check`, no type check, and the Playwright e2e suite is not in CI at all**
— the specs written _because_ "unit tests stayed green while five bugs shipped"
only run when someone remembers. Zero `@ts-check` pragmas, so the repo's
extensive JSDoc is decorative: nothing validates it.
**Fix, in order:** (a) add `vite build` + e2e to CI; (b) `jsconfig.json` +
`tsc --checkJs --noEmit` over `server/` and `ui/src/lib` (respects the no-TS
decision — the annotations already exist); (c) eslint with little more than
`no-unused-vars`.

### 7. Failures that never reach the user

One global `error` string is the whole failure surface, and every feed op clears
it. Catalogued silent failures: JobsPanel Cancel/Dismiss are fire-and-forget (a
rejected cancel leaves a zombie "running" row); `UpdateBanner.restart()` has no
catch and strands the button at "Restarting…"; SnapshotStrip renders a failed
sample as an empty strip; TreeSidebar root-load failure renders as "empty
library"; a RAW whose preview fails is a permanently blank tile with no retry.
**Fix:** an error stack/toast with explicit dismiss, and a `.catch` at each site
above.

### 8. App.svelte — 4,569 lines, 130 functions, 69 reactive statements, no unit tests

144 of 394 commits touch it. **The duplication `CLAUDE.md` warns about is
substantially fixed** (`withFeedTransaction` is the single window-replace guard) —
that note is stale and should be updated. What remains: the counts-cache reset
block is copy-pasted 4×, and the feed-window state machine is entangled with DOM
scroll side-effects.
**Fix:** two surgical extractions, no rewrite. (a) a framework-free
`feedWindow.js` controller — this converts the app's most bug-productive logic
(#35/#36/#39/#75/#77) from "only testable in Playwright, which CI doesn't run"
into plain vitest; (b) selection + undo, already self-contained.

## P3 — scale ceilings, not yet hurting

- **Content hashing is fiction at scale:** `hashPendingPhotos` runs once per scan
  with `limit: 50` and both callers drop the `remaining` flag — **100 of 114,125
  photos are hashed**. The "keyed by content hash" invariant does not hold, and
  `backupCoverage` is inert. Either loop on `remaining` behind `whenIdle()`, or
  strike the claim from the docs.
- **Stale rows are never purged:** no `DELETE WHERE stale = 1` exists anywhere.
- **`getCacheBreakdown` / `pruneOrphanedCache`:** ~500k synchronous
  `existsSync`+`statSync` on the event loop at 100k photos — opening the Manage
  Library breakdown wedges the whole server.
- **LoupeFilmstrip eagerly mounts 81 `<img>`s at a unique cold 64px cache
  bucket** — the exact issue-#90 mistake, re-shipped; every loupe open triggers 81
  cold thumbnail generations competing with the ±3 full-res prefetch.
- **`/api/image` and `/api/video` are not marked `interactiveRoute`**, so the
  loupe — the most latency-sensitive surface — competes head-on with a running
  metadata sweep. Conversely `whenIdle()` has no progress floor, so an active
  scroller can starve the sweep forever.
- **`metadata()` fans out 50 concurrent subprocesses** for a video-heavy batch.

## Infovis — the visualizations quietly lie

- **The timeline density is a sample and never says so.** The server returns
  `{sampled, total}` precisely so the client can disclose it; `App.svelte` throws
  both away. Above ~12k photos the KDE you brush to find trip gaps can contain
  sampling artifacts indistinguishable from real gaps — in the one view that
  drives the album-boundary decision. One prop and a "sampled from N" label.
- **The album auto-threshold is statistically wrong for its data.**
  `mean + k·stddev` over inter-photo gaps, on a heavy-tailed distribution: one
  3-year gap inflates σ until everything collapses into one album — reported as a
  confident "1 albums" with no diagnostic, and the k-slider then tunes a broken
  statistic. Show the gap distribution (log-scale histogram) and/or offer a
  quantile threshold.
